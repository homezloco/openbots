# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

OpenBots: an open-source, self-hosted, model-agnostic multi-agent orchestration platform. The differentiator is a live, editable canvas of the agent hierarchy/routing — drag an edge to reroute, even while a run is executing. See `PLAN.md` for full scope, phase status, and a running "known gaps" list — check it before assuming something is finished. `docs/orchestration.md` and `docs/adapters.md` cover the two trickiest subsystems in depth.

## Commands

```bash
corepack enable && pnpm install        # first-time setup

pnpm dev                               # web + api + worker via turbo (without the worker, runs stay pending)
pnpm build / pnpm typecheck / pnpm lint  # across all packages
pnpm --filter @openbots/api typecheck    # single package
pnpm --filter @openbots/web typecheck

pnpm --filter @openbots/api db:generate  # after editing apps/api/src/db/schema.ts
pnpm --filter @openbots/api db:migrate   # apply pending migrations

docker compose up postgres redis -d      # local Postgres + Redis (Redis published on localhost:6380)
docker compose up api worker -d --force-recreate  # after backend changes, rebuild first:
docker compose build api                 # api and worker share one image (see docker-compose.yml)

pnpm --filter @openbots/api test:e2e     # real e2e suite — see "Testing" below
```

There is no unit test suite — `pnpm test` at the root is a no-op (no package defines a `test` script; only `apps/api` has `test:e2e`).

### Running the web app

The containerized `web` service used to fail intermittently in sandboxed dev environments on large tarballs like `next`/`@next/swc-*` (`ERR_PNPM_TARBALL_FETCH_TARBALL`, plain registry-fetch flakiness — `docker compose build api` was never affected, since the api image doesn't pull those packages). Fixed 2026-09-10 by giving pnpm a real retry budget in `apps/web/Dockerfile` (`fetch-retries`/`fetch-retry-mintimeout`/`fetch-retry-maxtimeout`, plus a lower `network-concurrency`) before the install step — confirmed with a real `docker compose build web` run completing cleanly. If it ever still fails repeatedly, fall back to running it locally instead of fighting the network:

```bash
pnpm --filter @openbots/web build
pnpm --filter @openbots/web start   # serves on :3000, talks to the dockerized api on :4000
```

### Testing

`apps/api/e2e/run.ts` is a real end-to-end suite (42 cases): it makes actual HTTP calls (including real Anthropic API calls) against a running stack — no mocks. It requires `docker compose up` (postgres, redis, api, worker) already running with a real `ANTHROPIC_API_KEY` in `.env`. Run it with `pnpm --filter @openbots/api test:e2e` (or `E2E_BASE_URL=... pnpm --filter @openbots/api test:e2e` against a different host). It signs up a fresh throwaway user each run and covers: explicit/auto/consensus routing, the reviewer/tier warning, usage tracking, the file-access tool (including a blocked path-traversal attempt), templates, encrypted credential storage, fallback-chain classification, security regressions (allowlist rejection, cross-graph IDOR on node mutation, run-ownership auth, add-existing-agent IDOR in both directions), the agent-conversation-history endpoint's direct-vs-routed distinction, genuine mid-run rerouting, write-tool/worktree isolation (including the symlink-escape fix), `/push` and `/pr` (including a real push against a local bare-repo remote and the push-injection-resistance case), and — the only one that waits on real wall-clock time — a scheduled trigger's real BullMQ firing. If you add a feature that involves routing, credentials, providers, or the write/push/schedule paths, add a case here rather than trusting manual curl checks; this suite has caught real bugs manual testing missed (see PLAN.md).

The file-access test's fixture (`/tmp/testrepo/README.md`, mentioning "Widgetizer") is **committed** at `apps/api/e2e/fixtures/testrepo/` and mounted into both the `api` and `worker` containers by `docker-compose.yml` (`./apps/api/e2e/fixtures/testrepo:/tmp/testrepo:ro`) — don't recreate this by hand with `docker exec`; that's ephemeral and silently stops working the moment the container is recreated (which is exactly what broke it before this was committed).

The write-tool/push fixture (`apps/api/e2e/fixtures/writable-testrepo*`, mounted `:rw` at `/tmp/writable-testrepo`, `/tmp/writable-testrepo-outside`, and `/tmp/writable-testrepo-remote.git`) is regenerated fresh before every run by `setup-writable-fixture.mjs` (folded into `test:e2e` directly — pnpm doesn't run pre-hooks by default in this repo). Three gotchas that cost real debugging time building this: (1) it **clears each directory's contents in place** rather than `rm`+recreating it — the containers are typically already running when this script executes, and deleting/recreating a bind-mounted directory detaches the container's view from the new one (it keeps seeing the old, orphaned inode), making the repo look "not a git repository" from inside the container even though the host filesystem looks fine; (2) since the containers run as root, anything they create in these mounts (worktree admin files, pushed objects) ends up root-owned on the host, so the script reclaims ownership via `docker compose exec worker chown` *before* touching anything — this silently no-ops if the containers aren't up yet, which is fine (nothing root-owned exists yet either); (3) the symlink-escape fixture and the push-target bare repo both need to resolve *inside the container* (where the orchestrator always runs, never on the host), so they're addressed by their container-side mount paths, not the host paths this script itself uses.

### CI

`.github/workflows/e2e.yml` runs the full e2e suite on every push to `main` and on manual `workflow_dispatch`, using the exact same `docker compose` flow as local dev (write `.env` from secrets → start postgres/redis → migrate → build+start api/worker → wait for `/health` → run the suite). It intentionally does **not** run on pull requests, since every run makes real, billed Anthropic API calls. Requires three repo secrets to be set (Settings → Secrets and variables → Actions) before it can pass: `ANTHROPIC_API_KEY`, `E2E_SESSION_SECRET`, `E2E_CREDENTIALS_ENCRYPTION_KEY` (the latter two can be any random 32-byte hex string, e.g. `openssl rand -hex 32` — they don't need to match your local `.env`, they just need to exist and be stable within a run).

## Architecture

TypeScript pnpm/Turborepo monorepo. `apps/web` (Next.js + React Flow) and `apps/api` (Fastify + BullMQ worker) both depend on `packages/graph-schema` (zod types, the single source of truth for the data model) and `packages/providers` (model-provider adapters built on the Vercel AI SDK). `apps/api/src/db/schema.ts` (Drizzle) is a hand-maintained mirror of `graph-schema` — there is no codegen link between them; changing one means manually updating the other.

### The orchestration engine never plans a run ahead of time

`apps/api/src/orchestrator/engine.ts::dispatchHop()` dispatches exactly one node, then calls `resolve.ts::resolveNextHop()` fresh — reading whatever the graph looks like *at that moment* — and enqueues one BullMQ job for the next hop if there is one. This is the entire mechanism behind drag-and-drop rerouting (editing an edge is just a row update; it's picked up on the affected run's next hop) and it means there is no single function that computes a run's full path. Read `docs/orchestration.md` before touching this file.

**`Run.mode` gotcha**: `pinned` (the default) snapshots the graph into `runs.graphSnapshot` at creation and *never* re-reads it — a routing edit made afterward has zero effect on that run, by design. Only `mode: "live"` re-resolves against the current graph on every hop. Forgetting this produces a run that silently ignores reroutes with no error (bit the e2e suite once already).

**Edge kinds** (`explicit` | `auto` | `consensus`) are resolved by three different strategies in `resolve.ts` and `engine.ts::dispatchConsensus()`. A `consensus` source node fans out to every edge in its `consensusGroup.edgeIds` concurrently (inline within one BullMQ job, not as separate queued hops — a deliberate v1 simplification), joins via a `fanout_batches` row, then dispatches `aggregatorNodeId` with every branch's output. `consensusGroup` can only be set via `PATCH /graphs/:id/nodes/:nodeId` — never at node-creation time, since it references edge ids that don't exist until the node and its edges already exist. The zod schema is `ConsensusGroup.nullable().optional()`, not just `.optional()`: `PATCH { consensusGroup: null }` is the only way to convert a hybrid node back to plain auto-only routing, and `.optional()` alone silently rejected that (there was previously no way to ever clear a set `consensusGroup` once a hybrid node no longer needed it).

**Hybrid auto/consensus nodes**: `consensusGroup.edgeIds` don't have to be `kind: "consensus"` edges — `dispatchConsensus` resolves them purely by id, so they can be a node's existing `auto` edges instead. A node with both `auto` edges and a `consensusGroup` is a hybrid: `dispatchHop` only fans out when the model's output starts with the sentinel `ALL` (taught via `appendAutoRoutingContext` whenever `node.consensusGroup` is set — same free-text-prefix convention as `UNKNOWN`, shared parsing logic in `resolve.ts::startsWithSentinel`); any other output falls through to normal single-target routing. A node with a `consensusGroup` and *no* `auto` edges keeps the original unconditional-fan-out behavior. `POST /graphs/:id/edges` auto-syncs a new `auto` edge into its source's `consensusGroup.edgeIds` when the source is already a hybrid node (deliberate: without it, adding a new specialist under an existing supervisor would silently miss it in every future `ALL` broadcast) — still overridable by PATCHing a specific edge id back out. `computeWarnings` also flags (non-blockingly) any remaining coverage gap.

### Every node row returned by the API must go through `nodeRowToAgentNode()`

Postgres stores position as flat `positionX`/`positionY` columns; `AgentNode` needs `position: {x, y}`. Returning a raw `.returning()` row directly (instead of mapping it) previously crashed the canvas with `t.position is undefined`. Same pattern applies to `AgentGraph` (`POST`/`PATCH /graphs` must return the fully-hydrated shape via `loadLiveGraph()`, not the raw update row, since `AgentGraph` requires `nodes`/`edges`/`warnings`). If you add a route that returns a node or graph, reuse the existing mapper — don't hand-roll another one.

### Providers, credentials, and tools

`packages/providers` wraps the Vercel AI SDK (`ai` v7 — note the `inputSchema`/`schema` naming, not v4's `parameters`) behind one interface per provider, each declaring capability flags (`streaming`/`toolCalling`/`vision`/`promptCaching`) rather than assuming uniform support. Credential resolution (`apps/api/src/orchestrator/credentials.ts`) checks, in order: a node-specific stored credential, then a graph-wide one, then an environment variable — stored credentials are AES-256-GCM encrypted (`apps/api/src/auth/crypto.ts`) and the plaintext never appears in any API response. `callAgent()` in `engine.ts` tries `node.fallbackChain` in order, but only falls through on a *classified* auth/model error (`providerErrors.ts`) — a generic bad-request never triggers fallback, since retrying identical bad input against a different provider won't help.

The tool registry (`packages/providers/src/tools.ts`) is intentionally a small built-in set (`calculator`, `current_time`, `read_file`/`list_directory`, `write_file`/`edit_file`, `pc_telemetry`), not dynamic npm-package loading — that would let anyone who can edit a graph run arbitrary code in the API process. Every file tool is parameterized per-node by `AgentNode.fileAccessRoot` and enforces its path boundary via `resolveWithinRoot()` — both the tool name *and* a configured root are required (defense in depth; neither alone grants access). `resolveWithinRoot` is more than a lexical `path.relative()` check: it walks up from the target to the nearest existing ancestor and `fs.realpath`s it, so a symlink inside the root pointing outside it can't be used to escape — a real, found-in-review gap the lexical-only version had (see PLAN.md's security review).

### Prompt caching: a cost-accounting fix for everyone, an opt-in behavior change for Anthropic

Two independent things live under this name. **Cost accounting** (`packages/providers/src/pricing.ts::estimateCostUsd`) always prices a call's `noCacheTokens`/`cacheReadTokens`/`cacheWriteTokens` separately (from the AI SDK's own cross-provider-normalized `LanguageModelUsage.inputTokenDetails`) rather than treating every input token as full-price — this matters even with zero OpenBots configuration, since OpenAI's own prompt caching is automatic and free server-side (no opt-in anywhere), and without this the dashboard would silently overestimate cost for any OpenAI node with a long-enough prompt. **The opt-in** is Anthropic-specific: `ANTHROPIC_PROMPT_CACHING` (env var, off by default) makes `engine.ts::callAgent` attach `cache_control: {type: "ephemeral"}` (5-minute TTL) to the hop's system prompt — the one thing resent byte-identical on every hop dispatched to the same node. This needs the `messages` array form of `generateText()`, not the `system`/`prompt` shorthand strings, since `providerOptions` can only be attached to a message object; `buildPromptOptions()` returns the untouched shorthand form whenever the flag is off or the provider's `promptCaching` capability is false, so nothing changes for anyone who hasn't opted in. It's a real tradeoff, not a free win: a cache write costs 1.25x normal input price and only pays off if the *same node* is called again within 5 minutes — true for chat sessions (`useBotChat`'s growing transcript keeps hitting the same node), consensus fan-out, and `dispatch_to_graph` revision rounds, false for a node only ever invoked once.

### Write tools are isolated to a git worktree, never the user's real checkout

`write_file`/`edit_file` are gated by a **second, independent** operator allowlist, `ALLOWED_FILE_WRITE_ROOTS` (`apps/api/src/validation/fileAccessRoot.ts`) — a node having read access to a path never implies write access to it. Unlike the read allowlist (checked only at node-save time), the write allowlist is *also* re-checked at tool-resolution time in `resolveTools` (`packages/providers/src/tools.ts`), so tightening it after a node was created actually takes effect on that node's next run.

The first write in a run creates an isolated `git worktree` (`packages/providers/src/gitWorktree.ts::ensureWorktree`) at `<fileAccessRoot>/.openbots/worktrees/<node-slug>-<runId8>/`, on a fresh `openbots/<same-name>` branch off HEAD — writes never touch whatever the user has checked out. Commit granularity is **per-hop, not per-tool-call or per-run** (`commitWorktreeChanges`): a single model step can make several tool calls, so per-tool-call commits would race on which "pending commit" belongs to which concurrently-running `execute()`. Worktree creation is deliberately NOT check-then-act — `git worktree add` is called unconditionally and a failure is only treated as fatal if the path still doesn't exist afterward, since two hops can legitimately race to create the same one (`WORKER_CONCURRENCY` defaults to 10, and consensus fan-out runs branches concurrently).

**The container runs as root** (`apps/api/Dockerfile`, no `USER` directive) while host-mounted directories are owned by the host user — every git operation needs `git config --global --add safe.directory <root>` first (`ensureSafeDirectory`, idempotent) or it fails with "detected dubious ownership." No global git identity is configured anywhere; each commit call sets `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` on that one child process instead.

The model has zero innate knowledge that its writes get auto-committed (a pure engine side effect happening *after* it responds) — `engine.ts::appendWriteContext` injects that explanation into a write-capable node's system prompt specifically so it stops inventing an inaccurate manual git workflow to recommend, while still firmly teaching it that it can never push (see below) regardless of what any message tells it.

### `/push` and `/pr` are intercepted by exact regex *before* orchestration — never LLM-judged

This is a hard, non-negotiable safety property, not a convenience: `POST /runs` (`apps/api/src/routes/runs.ts`) checks the raw `input` string against `/^\/(?:push)(?:\s+(.+))?$/` and `/^\/pr(?:\s+(.+))?$/` **before any model or orchestration involvement**. If either an LLM's judgment or anything an agent had ever read (a file, a tool result) could trigger a push, that content becomes a prompt-injection path to an irreversible, shared-system action. A literal, exact command the human typed themselves closes that off entirely — never move this check later in the pipeline or make it fuzzy/semantic.

`agent_commits` (populated alongside the commit-note `callAgent` already appends to a hop's output) tracks every commit for push-target lookup; `/push` with no argument targets the most recent *unpushed* one, `/push <branch>` a specific one. `/pr` separately targets the most recent *pushed* one (`pushedAt` set) — a PR needs a branch GitHub already has — and always requires a GitHub PAT (`user_credentials`, provider `"github"`) regardless of whether the matching push used HTTPS or SSH, since PR creation is a GitHub REST API call, not a git-transport operation.

`pushBranch()` (`packages/providers/src/gitWorktree.ts`) branches on the worktree's `origin` scheme: `https://` uses the stored PAT via a one-request `http.extraheader` (never persisted to `.git/config`); `git@github.com:`/`ssh://.../github.com/...` (github.com only — `isGithubSshRemote`) uses a stored SSH private key (`user_credentials`, provider `"github_ssh_key"`) written to a 0600 file inside a fresh 0700 temp dir for the duration of one push and deleted immediately after, with `GIT_SSH_COMMAND` pinned to GitHub's own published host key (fetched from `https://api.github.com/meta`, hardcoded rather than trusting `ssh-keyscan` on first connection — exactly what host-key pinning exists to prevent) and `BatchMode=yes` so a passphrase-protected key or host mismatch fails fast instead of hanging a worker; any other scheme (a local/file path — what the e2e suite pushes against) falls through to a plain push, still needing `ensureSafeDirectory` on the *remote* path too, since a local push hits the same dubious-ownership check the worktree itself does.

`user_credentials` is account-scoped (one row per `(userId, provider)`), deliberately separate from the graph/node-scoped `provider_credentials` (AI model keys) — a different shape for a different purpose, managed at `/settings` in the web app. Verified 2026-09-09 (a direct security question, not just an assumption): every route in `routes/userCredentials.ts` is `requireAuth`-scoped to `eq(userCredentials.userId, req.userId)`, and all three (`POST`/`GET`/`DELETE /me/credentials`) return only `{id, provider, label, createdAt}` — the plaintext is accepted once on create, immediately passed through `encryptCredential()`, and never returned by any response; decryption only ever happens in-memory inside a tool's own outbound call (`businessMetricsTool.ts`, `/push`'s PAT usage).

### Scheduled runs use BullMQ **job schedulers**, not the deprecated repeatable-jobs API

`scheduled_triggers` (`{graphId, cronExpression, mode, enabled, input, lastRunId, lastTriggeredAt}`) is backed by `queue/scheduleQueue.ts`'s `upsertJobScheduler`/`removeJobScheduler` — BullMQ 5.x's current API. `getRepeatableJobs`/`removeRepeatableByKey` still exist but are deprecated for removal in v6; don't reach for them in new code. The trigger's own id doubles as the `jobSchedulerId`, so registering is naturally idempotent — safe to call again on every enable/edit, and on every worker boot.

**Postgres is the source of truth, Redis a derived cache**: a BullMQ job scheduler persists in Redis independently of the app, so it normally survives a restart untouched — but Redis can be wiped separately from Postgres (e.g. a volume-separated `docker compose down -v`). `worker.ts::reconcileSchedules()` re-registers every `enabled` trigger from Postgres on every single boot (not just recovery) for exactly this reason. `DELETE /graphs/:id` explicitly unregisters a graph's schedules before the FK cascade removes their rows — Postgres cascades know nothing about Redis-side state, so skipping this leaves an orphaned scheduler firing forever into a "trigger not found" no-op with no way to stop it short of a Redis flush.

A firing (`orchestrator/scheduledTrigger.ts`) re-reads the trigger and its graph **fresh from Postgres** rather than trusting anything captured at registration time, and creates the run through the same shared `orchestrator/createRun.ts` helper `POST /runs` uses — a scheduled run is not a parallel reimplementation that could drift from a manual one.

### `dispatch_to_graph` lets one graph fire work into another — the one exception to "graphs are fully self-contained"

Everything above says routing edges only ever connect nodes within the same graph. `dispatch_to_graph` (`orchestrator/dispatchTool.ts`) is a deliberate, narrow exception: a node with it in `tools[]` and a `dispatchTargets: string[]` (graph ids) starts a real run in another graph via the same `createRun()` helper `/push` and scheduling use. The model only ever supplies a graph **name**; it's matched against a pre-authorized, pre-filtered candidate list resolved server-side, so even a fully prompt-injected tool call can at absolute worst dispatch to a graph already in that node's own `dispatchTargets`. Ownership (`target.ownerId === callingGraph.ownerId`) is re-verified fresh inside `execute()` on every call — never trusted from whatever `dispatchTargets` said when the node was last saved, the same "config is a save-time convenience, not the security boundary" pattern `fileAccessRoot`'s runtime allowlist re-check already follows.

**Agent-as-tool, not fire-and-forget (reversed 2026-09-11).** `dispatch_to_graph` used to return the instant a run was *created*, never seeing its result — deliberately, to avoid blocking a BullMQ worker slot on another graph's entire run. Real usage made that the wrong default: a Lead dispatching work wants to review the result and report back, the way Anthropic's own production multi-agent research system does ("our lead agents execute subagents synchronously... this simplifies coordination, but creates bottlenecks" — an accepted tradeoff, not a mistake, and the same shape LangGraph's supervisor pattern and CrewAI's hierarchical manager both use). So it now **blocks and returns the target run's real output**, bounded by a per-hop timeout budget that shrinks across repeat calls in the same hop (`engine.ts`'s `hopDeadlineEpochMs`, threaded into `callAgent` and `createDispatchToGraphTool`) so it can never hold a worker slot indefinitely — a target still running past that budget degrades to `outcome: "still_running"` rather than hanging, and `check_dispatch_status` can pick up the answer later. A dispatch-capable node's hop timeout is extended from the default 180s to `DISPATCH_HOP_TIMEOUT_MS` (600s) specifically because a blocking wait needs real wall-clock budget the default wasn't sized for — applied at **every** `withNodeTimeout` call site, including a consensus branch that happens to carry `dispatch_to_graph` (`dispatchConsensus`'s per-branch call), since one blocking branch extends that whole fan-out round. "Review it, then call again with revised instructions if needed" needed zero new engine primitive — each hop's `generateText` already allows up to 20 sequential tool calls (`stepCountIs(20)`), so a revision round is just the model calling the same tool twice; each call starts a brand-new run with no memory of the last one, so the model has to restate the full task. `WORKER_CONCURRENCY` (default 10) is the real cost of this: a blocking dispatch holds its own worker slot for the wait duration, on top of the target's own hop(s) each needing slots too — raise it if leaning on this pattern heavily.

**Cross-graph dispatch cycles are a genuinely new risk** — nothing before this tool could touch another graph's execution, so nothing needed a cycle guard. `runs.dispatchDepth` (incremented on every dispatch, capped at `MAX_DISPATCH_DEPTH`) is a required part of the tool, not an afterthought: Graph A dispatching into B whose own Lead dispatches back into A has no natural stopping point otherwise. This check runs and returns *before* any run is created or any waiting begins, so it holds exactly as before under blocking semantics — a depth-refused call fails fast regardless.

`dispatch_to_graph` and `business_metrics` (`orchestrator/businessMetricsTool.ts` — real conversion/revenue/traffic numbers from account-scoped `user_credentials`, provider names `metrics_<source>`, read-only hardcoded endpoints only, same rule `pc_telemetry` follows) both live in `apps/api`, not `packages/providers/src/tools.ts` — they need `db`/`createRun`/`decryptCredential`, all `apps/api`-only, and `packages/providers` must never depend on `apps/api`. `resolveTools()` silently skips any tool name it doesn't recognize, so both are merged into the resolved tool set by hand in `engine.ts::callAgent` instead — `packages/providers`' `listAvailableTools()` carries metadata-only entries for them so a future tool-picker UI shows them accurately without ever constructing them there.

### `run_code` never executes untrusted code in-process — it's always a network call to an already-isolated sandbox

Unlike every other tool, `run_code` (`orchestrator/codeSandboxTool.ts`) executes attacker-influenceable code — a categorically different risk than reading/writing bytes or calling a pre-authorized endpoint. The `worker` container has zero privileged/Docker-socket access, and that's never changing for this feature: `run_code` always delegates to something already built and hardened for exactly this, reached over the network, the same shape `dispatch_to_graph`/`business_metrics` already use for their own trust boundaries.

Pluggable across three backends behind one interface (`packages/providers/src/sandboxTypes.ts`'s `CodeSandboxProvider`, `sandboxRegistry.ts`'s `e2b`/`daytona`/`local` adapters — mirrors `ProviderAdapter`'s "one interface per LLM provider" shape), operator-selected via a single `SANDBOX_PROVIDER` env var, not a forced single vendor:

- **e2b** — Firecracker microVMs, hosted only (BYOK). `allowInternetAccess` defaults to `true` in the SDK — the adapter always passes `false` explicitly, never assumes the default is safe.
- **daytona** — hosted only since Daytona's core platform moved to a closed, private codebase in June 2026 (the public repo is frozen, no further fixes); full self-hosting is no longer possible, only a hybrid mode (runner on your own Kubernetes, control plane still on Daytona's infra) that doesn't fit this project's docker-compose model. BYOK, same shape as e2b. Its `process.codeRun()` has no separate stderr field (`result` is the command's combined output) — a real SDK limitation, not a bug in the adapter.
- **local** — self-hosted `ghcr.io/engineer-man/piston`, no BYOK credential, isolates via `isolate` (namespaces/chroot/cgroups). Lives in `docker-compose.yml` behind the `sandbox-local` profile — never starts unless the operator opts in with `docker compose --profile sandbox-local up`, and has no `ports:` entry (reachable only over the compose network by service name, never published to the host). Piston's own upstream `docker-compose.yaml` requires `privileged: true` for its isolation to manage cgroups/namespaces itself — a real, deliberate tradeoff for a genuinely self-hosted, no-BYOK option, scoped to this one dedicated container rather than a privilege grant to `worker`.

Dual-gate like everything else: `"run_code"` in `node.tools[]` AND the operator's `SANDBOX_PROVIDER` env var (empty = the tool is never merged into a hop's tools at all, however a node is configured — checked fresh in `engine.ts`, not just at node-save time). No per-node config field exists, unlike `fileAccessRoot`/`sshTarget`/`dispatchTargets` — there's nothing per-node to vary, since language support and the timeout ceiling are fixed platform-wide. BYOK credentials for `e2b`/`daytona` are owner-scoped `user_credentials` rows named `sandbox_<providerId>`, stored as a bare API key string (the `github`/`github_ssh_key` single-field pattern, not the `metrics_<slug>` JSON-blob pattern, since there's only one field to store) — deliberately not an operator-wide key, so a runaway agent loop's cost/quota risk falls on the node's own owner. Every sandbox call is stateless (a fresh sandbox per call, torn down in `finally` right after) and has no network access, hard-coded at the adapter level for all three backends, not configurable — a pure compute box, no exfiltration path except stdout/stderr, which get redacted (`redactSecrets`) and size-capped before reaching the model. An unredacted copy of `code`/`output` is still written to the `sandbox_runs` audit table before redaction, same ordering `run_remote_command` already uses and for the same reason (the account owner already has access to their own run history; only what reaches the LLM provider gets scrubbed). The timeout (`SANDBOX_TIMEOUT_MS`, default 60s, hard-clamped to 120s) is deliberately kept well under the default 180s hop budget, so — unlike `dispatch_to_graph` — `run_code` needed zero changes to `hopTimeoutMsFor`/`hopDeadlineEpochMs`.

### Auth

Cookie-based sessions using an HMAC-signed opaque token (`apps/api/src/auth/session.ts` — no session table, verification is a local recompute) and scrypt password hashing (`password.ts`) — deliberately avoiding bcrypt/argon2 native modules after repeatedly hitting Docker build network flakiness fetching large native binaries in this environment. **Fastify plugin gotcha**: `authPlugin` must be wrapped with `fastify-plugin` (`fp()`) — without it, `register()` creates an isolated encapsulation context, and `decorateRequest`/`addHook` silently never reach sibling route registrations (`req.userId` would be `undefined` everywhere except inside the plugin itself). This exact bug shipped once already, and the same class of bug hit `app.setErrorHandler(...)` too — it must be registered in `apps/api/src/index.ts` **before** any `app.register(...)` calls for the route plugins, or the already-created child contexts never inherit it (invalid bodies silently 500'd instead of 400'ing until this was reordered). Cookie `secure` is controlled by `COOKIE_SECURE`, deliberately *not* tied to `NODE_ENV` — a self-hosted "production" deployment very often still serves plain HTTP, and tying it to `NODE_ENV` silently breaks every login. CORS (`WEB_ORIGIN` env var, `credentials: true`) is required since the web app (port 3000) and API (port 4000) are different origins.

**Any Next.js page that calls an auth-required endpoint must be a client component.** A server component's server-side `fetch()` never carries the browser's session cookie — it'll 401 with an opaque "Server Components render" crash the moment an endpoint gains `requireAuth`, even though it may have "worked" fine while that endpoint was public. Follow the `GraphPicker`/`Dashboard`/`runs/page.tsx`/`hierarchy/page.tsx` pattern: `"use client"`, `useAuth()`, fetch in `useEffect`. `useSearchParams()` in a client component additionally needs a `<Suspense>` boundary or the Next.js build fails. `GET /graphs/:id` and `GET /templates` require auth (and ownership / author-scope); do not treat graph JSON as a public capability URL.

### `fileAccessRoot` and the operator allowlist

`AgentNode.fileAccessRoot` alone is not the security boundary — `ALLOWED_FILE_ACCESS_ROOTS` (comma-separated env var, `apps/api/src/validation/fileAccessRoot.ts`) is an *operator*-level allowlist that any per-node `fileAccessRoot` must be a subdirectory of, checked via `zod.refine()` at both the manual node route and quick-add. Secure by default: an empty/unset allowlist means no agent, however configured, can be granted file access at all. Keep every legitimate use case in the *same* comma-separated value — overwriting it for a new purpose (e.g. adding real project directories) silently drops previously-allowed paths (e.g. the e2e test fixture root) and breaks unrelated tests.

### `pc_telemetry` and local read-only integrations

`packages/providers/src/tools.ts`'s `pc_telemetry` tool talks to a sibling project (linux-command-centre) over its plain WebSocket (`PC_TELEMETRY_WS_URL`, default `ws://127.0.0.1:52341`) using Node's built-in global `WebSocket` — no new dependency. It only ever sends `{subscribe: channel}` for `thermal`/`battery` and reads the response; there is no message it can send that mutates anything. This is a deliberate pattern for any future "monitor an external local system" tool: read-only wire protocol in, no control/write path, full stop — see PLAN.md's "PC Health Monitor — capability boundary" for why control automation there was explicitly rejected even though it's technically wirable via a Polkit-gated helper.

For local development, reaching a host-bound service like linux-command-centre from inside the `worker` container needs `docker-compose.override.yml` (gitignored, never committed — standard per-operator Compose customization) setting `network_mode: host` on `worker`, which in turn requires overriding `DATABASE_URL`/`REDIS_URL` to `localhost` since host networking bypasses the Compose bridge network's service-name DNS.

### Auto-routing needs to be told its own candidates — and needs a way to say "I don't know"

A router/supervisor node's `auto` edges are resolved by matching its output against target descriptions — but the model dispatching that node has zero built-in knowledge of what those targets even are. `engine.ts`'s `getAutoRoutingTargets(graph, nodeId)` + `appendAutoRoutingContext(systemPrompt, targets)` auto-injects a formatted `{name, description}` list into any node's system prompt whenever it has outgoing `auto` edges (wired into both `dispatchHop`'s and `dispatchConsensus`'s calls to `callAgent`). Don't rely on a hand-written system prompt to enumerate its own routing options — it's easy to get away with in a hardcoded demo prompt and then fail silently (misroute) the moment a prompt is generated more generically (e.g. via quick-add). This is engine-level and automatic; no per-node prompt authoring should need to duplicate it.

`appendAutoRoutingContext` also teaches every auto-routing node a formal `UNKNOWN` convention ("start your reply with UNKNOWN" when it can't confidently pick), and `resolve.ts::matchAutoEdge` checks for that prefix (and for a zero keyword-overlap score) *before* scoring candidates, returning no match instead of guessing. This exists because of a real bug: without it, a genuine clarifying question that happened to name several candidates (since the injected context lists them by name) could win the keyword-overlap contest purely by accident, silently continuing the run instead of surfacing the question. `resolveNextHop` returning `{edge: null, nextNodeId: null}` makes `dispatchHop`'s existing "no next node → run completes with this output" path do the right thing with zero new plumbing — the clarifying question becomes the run's answer.

### Data model = one graph per session, not one global hierarchy

Each graph is a self-contained task/session with its own node hierarchy, routing, and run history — not a subtree of one universal org chart. This is deliberate: it scopes file-access grants, keeps conversation memory (see below) from bleeding across unrelated tasks, and templates (`agent_templates` — export a graph as a self-contained JSON snapshot, instantiate a deep copy with fresh node/edge ids) already solve "reuse this agent structure for a different task."

### Dashboard's chat memory has no backend component

`apps/web/lib/useBotChat.ts` implements multi-turn conversation memory entirely client-side: each new message's `run.input` is built by chaining the previous completed run's own `input` + `output` + the new message into one growing transcript string (`buildNextInput`). The engine has no concept of conversation turns — it just sees a longer prompt each time. Display recovers "just this turn's message" by taking the text after the last `"User: "` marker in the transcript (`extractLatestUserMessage`) rather than storing turns separately. This hook is shared by `BotChat` (single-node graphs, rendered directly in `dashboard/page.tsx`) and `HierarchyChat` (multi-node graphs — the live canvas plus the same input/transcript strip) so a multi-agent "team" gets identical conversation continuity to a single bot; `/hierarchy` itself has no chat memory and is unaffected.

**`send()`'s poll loop must never treat a non-`"completed"` status as success.** It used to give up after a fixed ~30s and fall through unconditionally to display whatever it last fetched — including a still-`"running"` run whose `output` is still `null` — rendered as the literal text `"null"` (`JSON.stringify(null)`). Real, shipped bug: `business_metrics` doing real external HTTP logins per source, chained across multiple tool-call steps, routinely takes longer than that. Now polls for up to 10 minutes and always surfaces a non-`"completed"` result as a thrown error instead.

### `HierarchyCanvas` needs `key={graph.id}` wherever its `graph` prop can change

It seeds `nodes`/`edges`/`graph` state from that prop via `useState(initialGraph)` — which, per React, does **not** re-run just because the prop changes on a later render. Both render sites (`app/hierarchy/page.tsx`, `HierarchyChat.tsx`) pass `key={graph.id}` specifically so switching graphs forces a full remount instead of silently reusing the previous graph's stale node/edge state. This bit the cross-graph gateway-node feature below the moment it existed (clicking a gateway node updated the URL and refetched server-side correctly, but the canvas kept showing the old graph) — any future spot that renders this component with a graph that can change needs the same key.

### The Hierarchy canvas visualizes cross-graph `dispatch_to_graph`/`manage_target_graphs` reach via synthetic "gateway" nodes

`node.dispatchTargets` is invisible on the canvas otherwise — a completely separate mechanism from `routing_edges`. `HierarchyCanvas.tsx` derives one gateway node per unique reachable target graph (dashed border, `id` prefixed `gateway:`) and one dashed edge per `(node, target)` pair (prefixed `gateway-edge:`) — the same "synthetic, UI-only, derived from config not a DB row" pattern the consensus fan-out's gather edge already established, so both `onReconnect`'s drag guard and any future edge-mutation code should check for either prefix, not just `edge.data` (the `edgesWithPulses` memo overwrites `.data` with `{pulses}` on every render, so a `.data`-based check there silently never fires — check `id.startsWith(...)` instead). Clicking a gateway node calls `router.push` to that graph's own `/hierarchy` view rather than opening the usual node-settings panel. No node position persists anywhere today, so a "↺ Reset layout" button and a bounded `nodeExtent` exist purely to give dragging an escape hatch, not because anything is saved.

### The run-events WebSocket is graph-scoped, and the auth check has to live in `preHandler`

`apps/api/src/ws/hub.ts`'s `GET /ws/graphs/:graphId/runs` is what lights up the Hierarchy canvas's node pulse/edge-signal animation live during a run. It used to be an unscoped `GET /ws/runs` with no auth at all — a real cross-tenant data leak, since it broadcast every user's run output/error text to any connected client. **The ownership check must be a `preHandler`, not logic inside the `(socket, req)` callback**: `@fastify/websocket` completes the HTTP upgrade (sends the 101) *before* that callback runs, so by then a normal HTTP 401/403 is no longer possible — only a post-hoc `socket.close()`, which still leaks that the handshake succeeded. `requireAuth` must come before `requireGraphOwner` in the `preHandler` array; `requireGraphOwner` alone has a latent gap (`ownerId !== req.userId` passes when both are `null` — an unauthenticated request against a graph whose owner was deleted). Every `publishRunEvent()` call in `engine.ts` now includes `graphId` so the hub can filter the shared Redis channel per-socket without a DB round trip per message. Both the canvas and the run detail page connect through the same `apps/web/lib/useRunEventsSocket.ts` hook (capped exponential-backoff reconnect) — add any new live-updating view through that hook rather than opening a raw `WebSocket` again.

### `run_events.nodeId` has no foreign key — on purpose

A node can move between graphs (see the project-agent consolidation) or be deleted, but its run history should stay queryable either way, so `runEvents.nodeId` (`db/schema.ts`) is a bare `uuid`, not a reference. This is what makes `GET /graphs/:graphId/nodes/:nodeId/conversations` (backs the canvas's click-an-agent-to-see-its-history slide-over, `AgentConversationPanel.tsx`) a simple query with no migration needed: every run a node has ever been part of, regardless of which graph currently owns it. The endpoint marks a run `isDirect` when the node was the entry hop (`sequence === 0`, i.e. the user talked to it directly) vs. one where another node routed to it. The event-card rendering itself lives in `RunEventTrail.tsx`, shared with the run detail page — don't hand-roll a second version of that markup.

### Docker build resilience

Both `apps/api/Dockerfile` and `apps/web/Dockerfile` use a BuildKit cache mount (`--mount=type=cache,target=/pnpm-store`) and filter the install to just that app's dependency tree (`pnpm install --filter "@openbots/api..."`) even though every workspace `package.json` must still be copied in for pnpm to reconcile the lockfile. This exists because this environment's Docker build network has repeatedly failed on large tarballs (`next`, `@next/swc-*`, `esbuild`) — if a build fails with `ERR_PNPM_TARBALL_FETCH_TARBALL`, it's almost always transient network flakiness, not a real dependency problem; retry before assuming something's broken.
